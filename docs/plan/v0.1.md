> Single source of truth for v0.1 scope and current state.
> This doc supersedes the former `v0.1-plan.md` and `v0.1-gaps.md`.
>
> [roadmap.md](roadmap.md) tracks the implemented pipeline and follow-on work.
> The broader language design is in [../spec.md](../spec.md); rationale
> explains design goals, not additional implemented v0.1 features.

---

## Goal

A minimal language able to write a **zero-overhead JSON parser** in Joyeer,
performance-comparable to C / C++ / Rust.

This is a performance goal, not a measured result. There is no checked-in
comparative benchmark suite or enforced runtime-size budget yet.

**Milestone status:** the native integration suite now compiles and runs a
Joyeer-written parser over external files. It covers the v0.1 JSON surface
(null, Boolean, integer, UTF-8 byte strings with the fixed escape set, arrays,
objects, whitespace, nesting, and selected malformed-input cases) and exits
with zero outstanding runtime-managed allocations. This demonstrates cleanup,
not allocation-free parsing or full JSON conformance.

A JSON parser exercises every minimum-viable language capability:

| Capability | Feature needed |
|---|---|
| Read string / file content | `String` + File I/O |
| Iterate bytes | byte indexing `s[i]: UInt8` + byte literals `b'x'` (spec §2.1.1) |
| Branch on `{`, `[`, `"` | `match` / `if-else` |
| Represent JSON values | `enum` (algebraic types) |
| Store key-value pairs | `Dict<String, T>` / `[String: T]` |
| Store arrays | dynamic `Array<T>` |
| Recursive parsing | recursive functions |
| Report errors | `Result` / `Optional` |
| Output results | `print` |

### Nice to Have

- [x] File read (`readFile(path: String): Result<String, IOError>`); binary-safe
    success plus typed missing/invalid-path errors and ownership cleanup are
    tested
- [ ] `Float` / `Double`

### Out of Scope for v0.1

- **User-defined generics** (generic `func` / `struct` / `enum`, type
  parameters, constraints, monomorphization) — see the decision below
- User-defined `init` / `deinit` bodies and explicit copy initializers; v0.1
    recursively manages compiler-known heap-backed values
- Top-level executable bindings/statements; put executable work in functions
  such as `main`. Parser/name-resolution acceptance does not imply global
  storage lowering.
- Closures / lambdas
- `for-in` (use `while` in the first JSON parser)
- `||` (the first parser only requires `&&`; conditional logic can use `if` / `match`)
- `??`, `?.`, postfix propagation `?`, and force unwrap `!` (use explicit `match`)
- Compound assignment such as `+=` (use `x = x + 1`)
- Match guards, alternative/range patterns, and tuple destructuring
- Traits / protocols / interfaces
- Concurrency / async
- Module system (single file is enough for JSON parser)
- adding a second backend; v0.1 lowers through Joyeer IR and LLVM
- **`break` / `continue`** (incl. labeled forms) and the `is` / `as`
  type-test / cast operators — deferred to v0.2 (spec §15); loops exit via
  their condition or `return`

## Decision: Generics in v0.1

**Short answer: no general generics in v0.1.** Split the concept in two:

| Kind | v0.1? | Why |
|---|---|---|
| **Built-in generic containers** — `Array<T>`, `Dict<K, V>`, `Optional<T>`, `Result<T, E>` | ✅ Yes | Implemented as **compiler/runtime-special-cased builtins**, *not* a general type-parameter mechanism. Dictionary lookup is currently linear. |
| **User-defined generics** — generic `func` / `struct` / `enum`, `<T>` declarations, constraints, monomorphization | ❌ No | The v0.1 target code (`JsonValue`, `Parser`) uses only **concrete types**. The JSON parser needs zero user-defined generics. |

Rationale:

- The [native target code](../../tests/native/json_parser.joyeer) defines no
  type parameters of its own: `[JsonValue]` and `[String: JsonValue]` are
  *uses* of built-in containers, not new generic declarations.
- A real generic system (type-parameter inference, constraints, and
  zero-overhead monomorphization) is large and tightly coupled to the memory /
  runtime-overhead commitments in [../rationale/](../rationale/). Doing it early
  would expand the milestone well beyond its current concrete-type workload.
- `Array<T>` / `Dict<K, V>` therefore stay on the **hard-coded builtin** path:
  the angle brackets are container syntax the compiler understands directly,
  with no general type-parameter machinery behind them.

User-defined generics remain follow-on design work (see [roadmap.md](roadmap.md)).

## Remaining Quality and Release Work

The executable JSON-parser milestone and its diagnostic-quality baseline are
implemented for the checked-in acceptance workload. Passing that workload does
not establish correctness for every program in the supported subset, JSON
conformance, or release readiness. Follow-on work includes broader type-directed
edits, multi-line/Unicode diagnostic rendering, machine-readable output,
optimized-value inspection, and standard-library work. Source line tables,
full lexical variable/type metadata, and native debug artifacts are available.

The reference JSON parser has known limitations beyond its deliberately
deferred floating-point and Unicode-escape support:

- `parseNumber` accepts leading-zero numbers such as `01`.
- `parseString` accepts unescaped control characters such as a raw newline.
- Decimal accumulation adds the ASCII byte before subtracting `b'0'`;
  even the valid `Int` maximum `9223372036854775807` can trap on intermediate
  overflow. Out-of-range input also needs a deliberate parse-error policy.

These are example-parser and coverage gaps, not reasons to disable the
compiler's checked arithmetic. Add focused malformed-input and boundary cases
before treating the fixture as a reusable JSON library.

Compiler checking now covers recursive payload exhaustiveness, evaluated
projection indices, proven restoration identity, loop re-entry, delayed
initializing-call effects, and nested argument/receiver accesses. These are
regression-backed foundations, not a claim of complete language soundness.
See the remaining gaps and precision limits in
[type checking](../impl/type-checking.md#8-known-correctness-gaps),
[semantic analysis](../impl/semantic-analysis.md#precision-limits),
[name resolution](../impl/name-resolution.md#7-known-resolution-gaps), and
[parser continuation](../impl/parser.md#5-newlines-commas-and-statement-boundaries).

Lowering/emission has native regression coverage for `&&` short-circuiting,
tag-guarded payload access, operand capture/cleanup timing, bounded loop stack
storage, concrete builtin-enum identity, and Optional binding conversion. The
[IR implementation notes](../impl/ir.md#7-evaluation-and-storage-invariants)
distinguish these invariants from the still-incomplete ownership, dominance,
and opcode-type verification.

Release work also includes third-party license/notice staging, excluding
GoogleTest's SDK from product packages, CI on supported platforms, and
performance/footprint measurement. See
[building.md](../building.md#release-staging) and
[runtime-overhead.md](../rationale/runtime-overhead.md).

String escape scanning/decoding is complete, so embedded JSON objects such as
`"{\"n\":42}"` no longer block the lexer. Deferred features can land after the
acceptance baseline without reopening v0.1.

The compiler lexer implements the deliberately small JSON-parser profile
defined in [../impl/lexer.md](../impl/lexer.md). That profile keeps
payload-carrying `enum` and `match`, but defers unrelated syntax sugar such as
`for-in`, match guards, range/alternative patterns, `??`, compound assignment,
interpolation, and the removed general effect syntax.

Lexical support alone does not make a future feature executable; additions
must traverse the complete native pipeline.

## Compiler Architecture Gaps

The following architectural foundations are implemented for the v0.1
acceptance workload; they are not claims that all edge cases are covered:

- [x] **Semantic analysis pass** — `let`/field immutability and access markers,
    all-paths-return, trailing-expression returns, unreachable warnings,
    definite initialization, and unused local/pattern warnings are enforced.
- [x] **Own IR (Joyeer IR)** — verified backend-neutral IR covers the JSON MVP.
- [x] **LLVM/native integration** — `--emit-llvm` writes text; Windows `-o`
    uses the bundled LLVM/LLD backend DLL.
- [x] **v0.1 ownership effects** — borrowing/inout/consuming/initializing,
    mandatory markers, use-after-consume, projection reinitialization, and
    call/argument-evaluation exclusivity are enforced for non-escaping storage.
- [x] **Heap-value copy and overwrite contract** — ordinary copies recursively
    clone uniquely owned storage, owned temporaries transfer directly, and an
    overwrite acquires its replacement before destroying the previous value.
- [x] **Diagnostics source rendering** — lexer and later stages emit stable
    IDs, severity, file path, one-based line/column, source excerpt, and caret
    range.
- [x] **Ownership diagnostic guidance** — access-marker insert/replace/remove
    fix-its and ownership-flow help are structured and CLI-tested.
- [x] **Parser/type diagnostic guidance baseline** — missing canonical parser
    tokens produce insertion edits and type mismatches provide expected/found
    help; both are structured and CLI-tested.
- [x] **Secondary diagnostic locations** — ordered same-source notes render an
    independent excerpt/range; overlapping-access diagnostics identify the
    first and later access without changing their stable ID.
- [x] **Context-aware diagnostic edits** — parser punctuation uses safe
    insertion/replacement/deletion edits with outer-delimiter protection;
    ownership access markers support insertion/replacement/deletion.

Broader type-directed edits beyond access markers are post-v0.1 quality work;
the compiler must not guess conversions for ordinary type mismatches.

## Native Runtime Status

The native runtime has recursive clone/destroy and deterministic
compiler-inserted cleanup for the current heap-backed surface. Whole-binding
and projection consuming ownership are implemented for the v0.1 surface.

- [x] **Native memory reclamation MVP** — scope/early-return cleanup and the
    runtime allocation-balance check cover strings, arrays, dictionaries,
    nested aggregates, and tagged payloads.
